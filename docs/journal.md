# Журнал замеров Burn Rate

Все замеры харнесса с 8 по 11 ноября 2026 года: что меняли, на каких задачах проверяли и что получилось.
Журнал нужен, чтобы видеть, как менялось решение, ловить ухудшения и брать отсюда цифры для README
и презентации.

## Как читать

- **Баллы** — по `tools/score.py`: «N / M», где M — сумма наград всех решаемых задач набора, N — набрано.
  Для coding засчитываются только задачи, прошедшие скрытые тесты.
- **Токены** — расход по правилам соревнования: выходные токены + входные / 10.
- **Режим.** *Обычный* — как у жюри: сначала решение без нейросети, остальное — агенту.
  *FAST_PATH=0* — все задачи решает модель; так видно расход и точность самого агента.
  *Без ключа* — только решение без нейросети (то, что требует модели, остаётся без ответа).
- **Наборы** описаны в конце журнала. Одинаковое имя набора — одинаковые задачи.

19 задач дошли до модели. Ошибка прогноза на задачу (MAE) и общий прогноз против факта:

| Прогноз | MAE | Общий прогноз |
|---|---|---|

По типам: math — MAE 17, search — 3 (прогноз хороший); data_analysis — прогноз 97 при факте 183.
У задач Марии маленькие таблицы и короткие условия, и модель по признакам предсказывала 65–88 токенов,
хотя один вызов стоит 115+. «Пол» это исправляет. Оговорка: проблема найдена на закрытом наборе,
поэтому для «пола» он уже не независимая проверка; пороги взяты только из обучающих трасс.

**Предел точности.** Даже ясновидец, знающий цену первого вызова, ошибается на 20 токенов: в 3 задачах
из 19 модель не справилась с первого раза и сделала второй-третий вызов (+70…+250 токенов). Это
случайность самой модели, по условию задачи её не предсказать. Итог: на задачах, похожих на обучающие,
оценщик в 2,6 раза точнее среднего; на чужих — на уровне среднего, а дальше упирается в случайность
модели. Следующий шаг — считать длину запроса точно (он собирается до отправки) и добавлять среднюю
надбавку на повторы: такой прогноз не зависит от похожести задачи. На баллы сейчас не влияет: харнесс
тратит 2–5 % бюджета, порядок задач ничего не решает.

## Подгонка под тесты у модели (coding_0090, 11.11)

`average` с двумя багами: `sum(xs) // len(xs) + 1`. Видимый тест — `average([2, 4, 6]) == 4`, скрытый —
`average([1, 2]) == 1.5`. Перебор находит «починку» `+ 0`, детектор подгонки отдаёт задачу модели, а
модель делает ту же минимальную правку: убирает `+ 1` и оставляет `//`.

| Вариант (seed 501, обычный режим) | Прогонов | Баллы | Токены |
|---|---|---|---|
| `develop` | 3 | 293 / 297 каждый раз | 1 071–1 609 |
| `develop` с эскалацией на reasoning | 1 | 293 / 297 | 1 079 |
| Общий совет в промпте (#46) | 2 | 293 / 297 | 1 597, 1 071 |
| Подсказка от детектора: «в `average` видимые тесты не ловят второй баг» | 2 | **297 / 297** | 1 098, 1 101 |
| То же, текст Сергея (#59, плюс деление и индекс) | 2 | **297 / 297** | 1 120, 1 107 |

Общий совет модель не останавливает, а адресное предупреждение с именем функции — да. Подсказка
добавляется только там, где сработал детектор: около 5 токенов на такую задачу.
